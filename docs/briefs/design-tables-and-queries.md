# Tables and key queries on every data store's panel

The owner asked: "to the DB modals add the tables that would be created and key queries; do so for all designs". On a design page, clicking a box opens its panel. `Component` (src/designs/types.ts) now has two optional fields, each a list of `Example` ({ title, lang: 'sql'|'json'|'proto'|'http'|'text', code, note? }):
- `tables`: what the box would hold. For a relational database: CREATE TABLE statements with keys, the indexes that matter, and partitioning where the page uses it. For a key-value store, cache, RocksDB, a wide-column store or a search index: the key layout and value shape (lang 'text'), one block per keyspace or column family. For an object store: the bucket and object path layout and one manifest or metadata object. For a log such as Kafka only if the box is the data's home: topics, key, partitions, retention.
- `queries`: the three to six reads and writes that matter most to this design, each as it would really be run in that store's own language (SQL; for RocksDB, Redis, Cassandra, S3 and the like, the actual commands or API calls as text), with literal example values from the page's own story, and a `note` saying when it runs, which index or key it uses and roughly how often or how fast if the page already has that figure.

Your job, for ONE design file named in your prompt: find every component that stores data (not only `kind: 'store'`: also a primary database drawn as a node, replicas, a vault, a feature store, a per-node local store, an archive) and give each `tables` and `queries`. Skip boxes that hold no data of their own. If a box only mirrors another (read replicas), give it the queries that run there and a one-block `tables` saying it holds the same tables, by reference, not a copy of the DDL.

Rules:
- Read the whole design file first. Everything you add must agree with what the page already says: names, ids, columns, example values, numbers, technology (`tech`, `built`), and any DDL or SQL already shown on the connections (`flows[].examples`). Where the page already shows a table on a connection, the component's `tables` must be the same table (same columns and names); do not invent a second schema. It is fine, and wanted, for the component panel to gather the full set of tables in one place.
- This is a teaching page read the morning of a systems design interview. Prefer the few tables and queries someone would draw on a whiteboard, complete enough to be correct: primary keys, the unique keys that give idempotency, the index each key query uses, partition or shard key. No filler columns.
- Each code block: lines at most 72 characters, at most about 25 lines; split a long schema into several titled blocks. Titles are short and say what the block is ("accounts: the balance cache", "Newest 50 entries for an account").
- Plain British English in notes, short sentences, no em dashes, concrete values. State what is simplified.
- Do not change anything else in the file: only add `tables` and `queries` to components (place them after `numbers` or `built`). No git commands. Edit only your file.
- Check SQL where you can: `@electric-sql/pglite` (PostgreSQL 18) is installed in /tmp/pgtest; write new files only under /tmp/pgtest/db-<design>/ and run your CREATE TABLE and query blocks there. Say in your report which blocks you ran. Non-SQL stores cannot be run: keep to commands you are sure of and list them as unverified.
- When done, from the repo root run `npx tsc --noEmit` and `npx vitest run`. Look at one panel: `node .shots/db-look.mjs <design-id>/c/<component-id>` writes .shots/db-<...>-1440.png and -390.png; read them and fix anything that looks wrong (a block that scrolls sideways at 1440 means a line is too long).

Report back, briefly: which components got tables and queries (with counts), which blocks you ran, what you wrote from your own knowledge that is not already on the page, and anything on the page that your schema work showed to be inconsistent.
