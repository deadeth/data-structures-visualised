## 1. Service boundaries (new)
- Core Ledger Service owns `accounts`, `pending_holds`, `transactions` (journal headers), `ledger_entries`, `outbox_events`. It only reserves funds, enforces balances and keeps zero-sum accounting. It knows nothing about cards, merchants' lifecycles, statements or interest rates.
- Card Processor Service owns `card_authorisations`: the Visa/Mastercard ISO 8583 message lifecycle, merchant details, MCC, declines, incremental and partial captures.
- Credit Billing Service consumes settled ledger events asynchronously and owns `credit_balance_buckets` (by APR tier and grace-period eligibility), `credit_statements`, nightly micro-interest accrual (`accrued_unbilled_interest_micros`) and the payment allocation waterfall (fees, then interest, then highest-APR principal). This matches the review: interest accrues in billing's own records and reaches the ledger only as an INTEREST_CHARGE transaction at statement time. Remove the INTEREST_RECEIVABLE daily accrual pair between ledger accounts from the chosen design (keep it as an alternative: accrual inside the ledger for daily revenue recognition).
- Each service has its own database. No distributed two-phase commit. The existing Banking API / payments service stays the owner of bank payments and payroll and calls the Core Ledger the same way the Card service does (hold with source_type 'OUTBOUND_PAYMENT' or 'PAYROLL_BATCH').
Rename on the page: `ledger_transactions` -> `transactions`; `outbox` -> `outbox_events`; "Ledger API + Ledger DB" are the Core Ledger Service.

## 3. Cross-service flows (his section 3; show each as SQL and messages)
Synchronous authorisation, about 50 to 100 ms (his figure; label it his target):
 1. Card service inserts card_authorisations (INITIATED) and calls PlaceHold(idempotency_key = auth_id).
 2. Core Ledger, one local transaction: lock the account FOR NO KEY UPDATE, test available funds or credit against the soft limit, insert the hold (trigger raises held_balance), insert HoldPlaced into outbox_events. VERIFIED as one statement chain.
 3. Card service sets APPROVED with hold_id, or DECLINED. Retries reuse auth_id.
Asynchronous settlement and expiry (outbox + Kafka/CDC):
 1. Clearing file arrives; Card service marks CLEARING_SUBMITTED and emits SettleCardTransaction through its own outbox.
 2. Core Ledger's settlement worker, one transaction: lock accounts in id order; hold ACTIVE -> CAPTURED (or, if already EXPIRED on a late force-post, no release); insert the header and paired entries; insert TransactionPosted. VERIFIED, including the late case.
 3. Card service consumes TransactionPosted (or HoldExpired from the expiry job) and sets CLEARED / EXPIRED. Billing consumes TransactionPosted too.
Self-healing reconciliation: a nightly job on replicas checks APPROVED authorisations <-> ACTIVE holds and CLEARED authorisations <-> POSTED transactions, one to one, and raises a break for each mismatch. Give the two queries in outline (they run against two databases, so the job exports keys from each and compares; say that).
Failure cases to cover (drills and the story): Card service crashes after PlaceHold succeeded but before APPROVED is written (on restart or retry the same auth_id returns the same hold; an INITIATED row older than a few seconds is retried or voided; the parity job catches leftovers); PlaceHold times out (the network gets a decline or stand-in; the hold, if it was placed, is voided by a follow-up VoidHold keyed by auth_id); SettleCardTransaction delivered twice; TransactionPosted consumed late; a hold expires then clears.
